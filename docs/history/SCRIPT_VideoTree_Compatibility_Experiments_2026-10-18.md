# SCRIPT 框架内的 VideoTree 兼容消融实验

最新资源策略：取消自设 GPU 总量上限，独立实验共同排队；验收依赖仍保留，资源由集群限制和实际可分配情况决定。有限作业完成或失败后自动退出释放资源。历史两卡或三卡设置不再作为人为约束，见 `jobs/resource_policy.json`。

2026-10-19 调度更新：取消与其他实验之间的人为串行依赖，兼容性检查 `674288` 已可独立排队。五题检查、完整基线验收和后续消融的内部依赖保持不变。当前所有作业各申请一张卡，small 队列允许每用户三个运行作业，因此可并行最多三张 H200。下文两卡及顺延安排是历史提交记录，当前以 `jobs/scheduling_override_20261019.json` 为准。

本轮先在 SCRIPT 的正式查询入口中复现原 VideoTree，再逐项开启 SCRIPT 的模块。全部配置调用 `script_core.controller.answer_query`，共用 Memory、Meter、Store、资源预算、结果格式和局部视觉执行器。原有常规读取默认配置继续保留，兼容模式通过显式配置开启。

这与此前独立的 g7 答案组合回放不同：基线检索、树扩展、原 QA、反馈、视觉核验和最终选择都在单次 SCRIPT 查询的生命周期内完成；g7 的历史预测不作为新推理输入。

## 兼容起点

`configs/script_videotree.yaml` 关闭全部扩展。查询执行三个原算法工具：

1. `videotree_width`：调用未修改的原 `adaptive_breath_expansion.launch`，使用原聚类、相关性评分、重试和宽度扩展规则。
2. `videotree_depth`：调用原深度聚类和代表帧选择函数，保持每层四个子簇的原参数。
3. `videotree_qa`：使用原 PromptFactory、Qwen.forward、A–E 选项顺序和答案解析，保留原提示中的 `None` 示例等格式细节。

权重由 SCRIPT 模型 worker 管理，适配器注入已有模型，不改变原算法。关闭扩展时不调用 SCRIPT 的问题解析、语义停止判断或 JSON QA，不做在线视觉观察。原特征和秒级描述缓存保持不变；M0 也复用已有相同版本，未重新衡量冷启动建库成本。

本轮兼容输入范围为完整 EgoSchema 视频、五个选择和原一秒描述网格。范围不满足时明确失败，不擅自改写时间或换问答格式。

## 九组配置

每组固定相同 300 题、同模型、同一秒级描述和特征。图、反馈和视觉先单独测试，再组合。

| 组别 | 相比父组的变化 | 父组 |
| --- | --- | --- |
| c0 | SCRIPT 框架内原 VideoTree，扩展全部关闭 | 原基线 |
| cg | 图检索补充至多 12 条原始秒级描述，原 QA 不变 | c0 |
| cf | 一轮检索反馈，补充至多 12 条尚未选中的描述 | c0 |
| cv | 具体缺口规划及至多两次局部视觉观察、核验 | c0 |
| cgf | 同时启用图检索与描述检索反馈 | cg |
| cgfv | 在图与反馈后加入局部视觉核验 | cgf |
| cp | 对扩展造成的改答加入原 VideoTree 答案保护 | cgfv |
| cqa | 最终 QA 替换为 SCRIPT direct JSON，选项仍按原顺序 | cgfv |
| corder | 仅把 SCRIPT QA 的选项展示换为内容哈希顺序 | cqa |

图检索只增加真实源描述，保持原选中描述及原 QA 模板；同一时刻不重复加入。图本身是来源可追溯的描述候选索引，不进入已核验像素事实表。若没有新增描述，不额外调用候选 QA。

反馈模块只返回缺口、待补描述和中立视觉问题，不直接返回替代答案；原答案作为待检查假设。局部核验使用现有 SCRIPT Materializer 的 `observe → verify_claims`，不预设候选结论；没有有效视觉事实时不会为视觉分支额外重答。

`cp` 只允许新增且完整核验的视觉过程事实触发改答，要求至少三个来源帧、过程可见并经独立区别审核。无区分事实、审核失败或不确定均保留本次查询内部的原 VideoTree 答案。此规则偏保守，仍须统计修对、改错和拒绝的有益候选，不能保证准确率单调上升。

`cqa` 改的是完整 QA 接口，包括输入表示、指令和约束解码，不能将差异归因为 JSON 单一因素；选项排序另列为 `corder`。基线中间答案仍用于反馈和保护，替换的是最终候选 QA 组件。

## 两道验收再释放消融

第一道是五题运行检查：每题执行九组配置，检查原树、原提示、原预测和原输入 token 数，并检查扩展模块能运行且不超预算。不以这五题准确率筛选方案。

第二道是完整 300 题的 c0 运行。**历史 299 道成功题必须逐题对齐树节点、system/user 提示、预测和输入 token 数，才允许正式消融开始。** 历史唯一失败题单列，其新运行成功或失败均计入 300 题分母，不伪造一个历史预测来凑准确率。若重现检查失败，后续作业依赖不会释放，失败题及字段保留在 `baseline_gate.json`。

这样先确认 SCRIPT 模板中的兼容基线成立，再解释各模块的得失，而不是只看到总准确率接近就称为兼容。

## 共享计算与成本

原树和原 QA 在 c0 中从预处理输入重新执行，正式 c0 不复用五题诊断结果。后续配置仍调用相同的原工具接口；对精确相同的输入，共享本轮 c0 及已有同题调用的工具缓存，避免无意义重复推理。缓存按问题、输入、模型、原源码和特征内容校验，不混用不同问题或不同输入。

每组记录实测在线耗时、缓存命中，以及若独立执行仍需的公共依赖处理时间。共享依赖会扣减该组 600 秒预算，不能通过缓存获得额外推理额度；同一查询中的同一依赖只计一次。预算和真实 GPU 时间分开保存，不能把缓存命中后的短延迟当作完整端到端加速。

已完成的无问题图抽取结果可在前轮任务结束后冻结复用；未完成或缺失的图按相同文本抽取方法补建。复用的历史图成本与本轮在线耗时分列。原树特征、原描述、M0、源代码、模型版本和输入包均留有内容哈希，标签只在验收和评分中读取。

## 调度和结果

实验目录为 `workdirs/script-videotree-compatible-300-20261018-r1/`。后台按以下依赖执行，包含现有作业在内最多同时使用两张 H200：

1. 现有 summary 图作业结束后，单卡五题诊断并冻结可复用的文本图。
2. 诊断成功，两个 GPU 作业运行 c0，每卡两个独立进程。
3. CPU 验收作业核对完整基线。
4. 验收通过，两个 GPU 作业运行其余八组，每组同样 300 题。

`jobs/submissions.json` 保存真实作业编号和依赖；`smoke/status.json` 保存五题检查；`baseline_gate.json` 保存完整兼容性验收。分组日志为 `shards/*/baseline.log`、`shards/*/variants.log`。

2026-10-18 已提交并解除提交前的人工保持：五题诊断 `674288`，完整基线 `674290` / `674292`，基线验收 `674294`，扩展消融 `674295` / `674296`。后续按用户的新方案调整排队顺序：`673540` / `673541` 结束后，先执行场景按需建图实验 `674405` → `674406` / `674407`，再释放本组诊断 `674288`。本组冻结源码和配置未改变。新作业的 `H` 是调度依赖保持，无须再次手动释放。若本组诊断或兼容性验收失败，后续依赖保持不会自动越过失败继续执行。

验收只做 CPU 比较，但 Hopper 的 small 队列要求至少分配一张 GPU，因此验收作业也保留一张卡的调度资源（不进行 GPU 推理，最长 30 分钟）；这一分配同样计入最多两张卡的限制。
